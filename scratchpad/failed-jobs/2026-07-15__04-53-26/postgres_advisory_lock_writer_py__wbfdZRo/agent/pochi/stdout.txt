# Serialized Single-Writer Guard for LanceDB using PostgreSQL Advisory Locks ## Background Multiple worker processes need to upsert into the same LanceDB table concurrently. LanceDB uses optimistic concurrency for commits, so naive concurrent writers can lose updates, produce torn/inconsistent rows, or race when assigning a shared monotonically-increasing sequence number. To make the write path safe you will serialize writers using a PostgreSQL **advisory lock** (`pg_advisory_lock` / `pg_try_advisory_lock`) as a cross-process coordination primitive. A local PostgreSQL server is already running inside this container purely as a lock coordinator; you must NOT contact any external network or hosted service. A local LanceDB database is also already initialized. ## Requirements Implement a Python module `solution.py` that exposes two callables: * `guarded_write(writer_id, rows) -> int` * `try_write(writer_id, rows) -> int | None` Both take a `writer_id` string and `rows`, a list of dictionaries each with the keys `id` (int), `value` (int), and `vector` (a list of 8 floats). All rows passed in a single call share the same `value`. `guarded_write` must: * Acquire a single, process-global advisory lock in PostgreSQL, **blocking** until it is held. * Inside the critical section, assign the next value of one global, monotonically increasing integer sequence that starts at 1 and is strictly contiguous across all writers (no gaps, no duplicates). Every row written by a single call gets that same sequence number. * Stamp each row with its `writer_id` and the assigned sequence number, then upsert all rows into the LanceDB data table keyed by `id` (existing ids are replaced, new ids inserted). * Append exactly one record to the LanceDB audit table describing the operation. * Release the advisory lock — and it MUST be released even if any step inside the critical section raises an exception. * Return the assigned sequence number. `try_write` must behave identically to `guarded_write` **except** that it acquires the lock non-blockingly (`pg_try_advisory_lock`): if the lock is currently held by anyone else, it must return `None` immediately without writing anything or consuming a sequence number; otherwise it performs the same work and returns the assigned sequence number. ## Implementation Hints * Project path: `/home/user/myproject` (put your module at `/home/user/myproject/solution.py`). * Connect to PostgreSQL using the standard `PG*` environment variables (`PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`); `psycopg2` is installed. * The advisory-lock key is the integer in the environment variable `PG_LOCK_KEY`; every acquisition must use this exact same key so all writers contend on one lock. * Connect to LanceDB at the path in the environment variable `LANCEDB_URI`. * The run id is in the environment variable `ZEALT_RUN_ID`. The data table is named `records_<ZEALT_RUN_ID>` and the audit table is named `audit_<ZEALT_RUN_ID>`. Both tables already exist (empty) when the container starts; open them. * Data table columns: `id` (int64), `value` (int64), `writer_id` (string), `seq` (int64), `vector` (fixed-size list of 8 float32). Holding the advisory lock is what makes this read-modify-write safe. * Wrap the critical section so the lock is released with `pg_advisory_unlock` (or by closing the session) in a `finally` block.
