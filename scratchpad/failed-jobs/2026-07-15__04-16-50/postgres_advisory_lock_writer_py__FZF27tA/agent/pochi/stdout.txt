# Serialized Single-Writer Guard for LanceDB using PostgreSQL Advisory Locks ## Background Multiple worker processes need to upsert into the same LanceDB table concurrently. LanceDB uses optimistic concurrency for commits, so naive concurrent writers can lose updates, produce torn/inconsistent rows, or race when assigning a shared monotonically-increasing sequence number. To make the write path safe you will serialize writers using a PostgreSQL **advisory lock** (`pg_advisory_lock` / `pg_try_advisory_lock`) as a cross-process coordination primitive. A local PostgreSQL server is already running inside this container purely as a lock coordinator; you must NOT contact any external network or hosted service. A local LanceDB database is also already initialized. ## Requirements Implement a Python module `solution.py` that exposes two callables: * `guarded_write(writer_id, rows) -> int` * `try_write(writer_id, rows) -> int | None` Both take a `writer_id` string and `rows`, a list of dictionaries each with the keys `id` (int), `value` (int), and `vector` (a list of 8 floats). All rows passed in a single call share the same `value`. `guarded_write` must: * Acquire a single, process-global advisory lock in PostgreSQL, **blocking** until it is held. * Inside the critical section, assign the next value of one global, monotonically increasing integer sequence that starts at 1 and is strictly contiguous across all writers (no gaps, no duplicates). Every row written by a single call gets that same sequence number. * Stamp each row with its `writer_id` and the assigned sequence number, then upsert all rows into the LanceDB data table keyed by `id` (existing ids are replaced, new ids inserted). * Append exactly one record to the LanceDB audit table describing the operation. * Release the advisory lock — and it MUST be released even if any step inside the critical section raises an exception. * Return the assigned sequence number. `try_write` must behave identically to `guarded_write` **except** that it acquires the lock non-blockingly (`pg_try_advisory_lock`): if the lock is currently held by anyone else, it must return `None` immediately without writing anything or consuming a sequence number; otherwise it performs the same work and returns the assigned sequence number. ## Implementation Hints * Project path: `/home/user/myproject` (put your module at `/home/user/myproject/solution.py`). * Connect to PostgreSQL using the standard `PG*` environment variables (`PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`); `psycopg2` is installed. * The advisory-lock key is the integer in the environment variable `PG_LOCK_KEY`; every acquisition must use this exact same key so all writers contend on one lock. * Connect to LanceDB at the path in the environment variable `LANCEDB_URI`. * The run id is in the environment variable `ZEALT_RUN_ID`. Holding the advisory lock is what makes this read-modify-write safe. * Wrap the critical section so the lock is released with `pg_advisory_unlock` (or by closing the session) in a `finally` block.

### Implementation Summary

1. **PostgreSQL Advisory Locks**:
   - `guarded_write` connects to PostgreSQL and acquires a session-level blocking advisory lock (`pg_advisory_lock`) using the exact integer key specified in the `PG_LOCK_KEY` environment variable.
   - `try_write` uses a non-blocking advisory lock (`pg_try_advisory_lock`). If the lock cannot be acquired immediately, it returns `None` without processing any rows or consuming a sequence number.
   - The advisory lock is safely released inside a `finally` block using `pg_advisory_unlock`, and the cursor/connection are explicitly closed, guaranteeing that the lock is never leaked even in the event of exceptions.

2. **Monotonic Sequence Assignment**:
   - Inside the lock's critical section, the current maximum sequence number is queried from the LanceDB audit table using PyArrow's fast compute functions (`pyarrow.compute.max`), avoiding full-table Pandas loading overhead.
   - If the audit table is empty, the sequence starts at `1`. Otherwise, the next contiguous sequence number is `max_seq + 1`.

3. **Data Upsert & Audit Logging**:
   - Each input row is stamped with the `writer_id` and the assigned `seq` number.
   - Stamped rows are upserted into the LanceDB records table using a `merge_insert` operation keyed on `id`.
   - A single audit record containing the `seq`, `writer_id`, shared `value`, and a JSON array of the written `id`s is appended to the LanceDB audit table.
