## `hybrid_search` — design walkthrough

### 1. Table name resolution
`_get_table_name()` reads `ZEALT_RUN_ID` from the environment and returns `docs_<run_id>`, which is used identically for the MariaDB table and the LanceDB table.

### 2. Keyword search (`_keyword_search`)
Connects to MariaDB via PyMySQL using the five `MARIADB_*` environment variables and issues:
```sql
SELECT id FROM `docs_<run_id>`
WHERE  MATCH(body) AGAINST (? IN NATURAL LANGUAGE MODE)
ORDER BY MATCH(body) AGAINST (? IN NATURAL LANGUAGE MODE) DESC
```
Documents that do not match are excluded by the `WHERE` clause, so the returned list already represents the full keyword-ranked order (best first).

### 3. Vector search (`_vector_search`)
Opens the LanceDB database at `LANCEDB_PATH`, opens the same table, and runs:
```python
table.search(query_vector).metric("cosine").limit(None).to_pandas()
```
`limit(None)` fetches **all** rows so the cosine ranking is global (no artificial cut-off before fusion). Documents are returned ordered by ascending cosine distance (most similar first).

### 4. RRF fusion (`_rrf_fuse`)
For each list, every document at 1-based rank *r* accumulates `1 / (60 + r)` into a shared score dict:
```
score(d) = Σ  1 / (60 + rank_in_list_L)
           L ∋ d
```
Documents that appear in both lists benefit from additive contributions (the overlap-boost requirement). Documents absent from a list contribute nothing for that list. The final dict is sorted `(-score, id)` to satisfy descending-score / ascending-id tie-breaking, then truncated to `k`.

### Key properties
| Property | How it's met |
|---|---|
| Shared `id` key | Both engines return `id`; used as the dict key in `scores` |
| RRF constant = 60 | `_RRF_K = 60` |
| Overlap boost | Additive accumulation across both lists |
| Top-k | `sorted_results[:k]` |
| Deterministic | Pure arithmetic on fixed-order results; tie-broken by `id` |
| Exact output schema | `{"id": int, "score": float}` per element |
