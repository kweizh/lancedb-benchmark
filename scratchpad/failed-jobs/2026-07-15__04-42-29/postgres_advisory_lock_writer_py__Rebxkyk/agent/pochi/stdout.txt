# Serialized Single-Writer Guard for LanceDB using PostgreSQL Advisory Locks ## Background Multiple worker processes need to upsert into the same LanceDB table concurrently. LanceDB uses optimistic concurrency for commits, so naive concurrent writers can lose updates, produce torn/inconsistent rows, or race when assigning a shared monotonically-increasing sequence number. To make the write path safe you will serialize writers using a PostgreSQL **advisory lock** (`pg_advisory_lock` / `pg_try_advisory_lock`) as a cross-process coordination primitive. A local PostgreSQL server is already running inside this container purely as a lock coordinator; you must NOT contact any external network or hosted service. A local LanceDB database is also already initialized. ## Requirements Implement a Python module `solution.py` that exposes two callables: * `guarded_write(writer_id, rows) -> int` * `try_write(writer_id, rows) -> int | None` Both take a `writer_id` string and `rows`, a list of dictionaries each with the keys `id` (int), `value` (int), and `vector` (a list of 8 floats). All rows passed in a single call share the same `value`. `guarded_write` must: * Acquire a single, process-global advisory lock in PostgreSQL, **blocking** until it is held. * Inside the critical section, assign the next value of one global, monotonically increasing integer sequence that starts at 1 and is strictly contiguous across all writers (no gaps, no duplicates). Holding the advisory lock is what makes this read-modify-write safe. * Wrap the critical section so the lock is released with `pg_advisory_unlock` (or by closing the session) in a `finally` block.

## Design

### `guarded_write(writer_id, rows) -> int`
1. Opens a fresh `psycopg2` connection with `autocommit=True` (advisory locks in PostgreSQL are session-scoped, not transaction-scoped).
2. Calls `pg_advisory_lock(PG_LOCK_KEY)` — **blocks** until the lock is obtained.
3. Inside a `try/finally`:
   - Opens (or creates) the LanceDB data table `records_<RUN_ID>` and audit table `audit_<RUN_ID>`.
   - Reads the current max `seq` from the audit table to derive the next sequence number (empty table → starts at 1).
   - Stamps every incoming row with `writer_id` and `seq`, then performs a **merge-insert upsert** keyed on `id` (matched rows are updated, new rows are inserted).
   - Appends one audit record with `seq`, `writer_id`, `value`, and `ids_json`.
   - **Always** calls `pg_advisory_unlock(PG_LOCK_KEY)` in the `finally` block, even if any step raises.
4. Returns the assigned `seq`.

### `try_write(writer_id, rows) -> int | None`
Identical to `guarded_write` except it calls `pg_try_advisory_lock(PG_LOCK_KEY)`:
- If the lock is already held by another session → returns `None` immediately (no write, no sequence consumed).
- If the lock is obtained → performs exactly the same work as `guarded_write` and returns the sequence number.
